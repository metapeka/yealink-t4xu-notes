Yealink T4xU — результаты разбора прошивки

Дата: 2026-10-29. Стенд: WSL2 Ubuntu + Ghidra 12.1.4 (REA) + binwalk 2.3.3 + Python 3.12 (pycryptodome, capstone, ubireader).

Обозначения: [факт] — проверено на данных/коде; [гипотеза] — вывод без прямого доказательства.

2. Формат ROM

  • Тело после 0x80 зашифровано cypher3 (XOR+ADD, ключи 32 Б опубликованы Synacktiv). Поток перезапускается на каждом блоке: заголовок блока расшифровывается с индексом 0.
  • Блок: [0x80 заголовок][тело], block_total = align32(0x80 + length) (паддинг нулями/мусором, зашифрован вместе с блоком).
  • Поле cipher в заголовке блока задаёт внутренний слой:
cipher значение слои
0 нет внешний cypher3
1 LZMA внешний cypher3 → LZMA
3 cypher3 внешний cypher3 → внутренний cypher3
0x83 AES-256 внешний cypher3 → AES-256 (блок 16 Б), ключ = первые 32 Б RSA-расшифрованного трейлера
  • [факт] cipher=3 — ровно два слоя cypher3: c3(c3(body)) даёт LOADER (MLO) + U-Boot.
  • [факт] cipher=1 — LZMA в формате LZMA-alone, свойства 5D, dict 0x00040000, lc=3/lp=0/pb=2.
  • [факт] cipher=0x83 — в updater вызывается AES с длиной ключа 0x20 (32 Б) и блоками по 16 Б (см. §5).

Вложенный контейнер заполняет тело app ровно: 0x80 + 0x2F83AC0 = 0x2F83B40, своего хвоста у него нет.

5. Апдейтер (version-блок)

108.86.0.118 — проверок содержимого нет

  • Импортов RSA/AES/SHA нет вообще (NEEDED пуст).
  • Строки открытым текстом: invalid rom hdr crc,0x%08x!=0x%08x, invalid blk hdr crc, invalid ROM hdr magic, unpack size invalid, rom or block file too small.
  • Есть прямой доступ к NAND: MTD Erase failure, MTD write failure, MEMWRITEOOB, flash.c, fwup_uboot, failed to update uboot1, update uboot1 fail, but update uboot2 success.

Вывод [факт]: этот апдейтер проверяет структуру (magic, CRC, размеры), а не подпись; блок bootloader пишется в uboot + вторую копию.

108.87.0.20 — RSA есть, но не над пакетом

  • Импорты: RSA_public_decrypt, RSA_size, d2i_RSA_PUBKEY_bio, SHA1/256/512, AES_*.
  • [факт] SHA вызывается ровно из трёх мест, все — helpers деривации ключа: SHA1←0x7da64, SHA256←0x7deb4, SHA512←0x7e184. Больше хеширования в бинаре нет.
  • [факт] memcmp в импортах отсутствует; сравнения расшифрованного дайджеста не найдено.
  • Путь в 0x7f778: memcpy(dst, *__xxx_rs, 0x200) → len -= 0x200 → ptr += 0x200 → FUN_0007e9c4(rsa, dst, 0x200, out) → только проверка «< 0».
  • Публичный ключ не лежит как DER/PEM (скан не нашёл OID 1.2.840.113549.1.1.1); собирается в рантайме: memcpy(&DAT_00086e98, 0x806) — таблица-перестановка, длина ключа 0x226 (550 Б = SPKI RSA-4096).

[факт] Куда идёт расшифрованный трейлер (ключевая находка). В 0x7f778 сразу после успешной RSA-операции (состояние 0x6916080d):

local_bc = &DAT_00099011;
memcpy(&DAT_00099011, local_58, 0xf0);      // 240 байт = размер AES-256 key schedule
FUN_00084414(local_bc, 0x20, local_24);     // AES_set_decrypt_key(key=32 Б, bits, schedule)

FUN_00084414 — это установка ключевого расписания AES (240 Б = 4*(Nr+1)*4 для AES-256): копирует ключ, считает Nk/Nr, разворачивает раундовые ключи.

То есть 512-байтный трейлер — не подпись содержимого, а зашифрованный ключевой блоб: RSA_public_decrypt(трейлер) даёт данные, первые 32 байта которых становятся ключом AES-256 для блоков с cipher=0x83. Отсюда и название crypto_type=0x83: это AES-256, а не «неизвестный шифр».

Следствия: 1. Без валидного трейлера ключ не восстанавливается → вложенный ROM не расшифровать (поэтому публичный тулчейн его и не умеет). 2. Трейлер можно не трогать при перепаковке — ключ от него не зависит от содержимого блоков. 3. Чтобы менять содержимое AES-блоков, нужен сам ключ: key = RSA_public_decrypt(трейлер)[0:32], а для этого нужен публичный ключ вендора, который собирается в рантайме в FUN_00082170 (DER SPKI 550 Б из хешей SHA1/SHA256/SHA512 + таблица DAT_00086e98, 0x806 Б).

[факт] Откуда берётся материал для публичного ключа. Вызов один (0x811a8):

r0 = *local_38 + *local_30      // указатель на 512-байтный блоб
r1 = 0x200                       // длина
r2 = *(*local_38 + 0x808)        // байт «типа»
bl  FUN_00082170

*local_38 — базовый образ (по коду рядом это результат mmap, т.е. сама прошивка/ELF в памяти), *local_30 — смещение, которое накапливается из байтов того же образа. То есть 512-байтный блоб лежит внутри образа, а не в трейлере.

Схема сборки ключа: SHA1 блоками по 16 Б → SHA256 блоками по 32 Б (обе стадии пишут в начало буфера) → SHA512 блоками по 64 Б со смещением +0x200 (проверено по ассемблеру вызова 0x825e4: add r2, r2, #0x200) → буфер 0x400 полностью заполнен → перестановка по таблице DAT_00086e98 (table[2] = 0x226 = 550) → DER SPKI.

[факт] Проверки не дали результата: полный перебор 512-байтных окон по всему version.elf (497 056 смещений) и первых 0x30000 байт расшифрованного ROM-потока — ни одного окна с префиксом 30 82 02 22. Значит либо базой таблицы служит не 0x76e98, либо входной блоб берётся из ещё не расшифрованного слоя (AES-256 0x83), либо индекс считается не так, как показывает декомпилятор.

Режим инструкций

  • [факт] точка входа ELF 0xdf1 — Thumb; функция 0x7f778 — ARM (push {r4,r5,r6,r10,r11,lr}; add r11,sp,#0x10; sub sp,sp,#0x110).
  • Бинарь смешанный; Ghidra определяет режим по функции. Кросс-проверка: ARM-скан нашёл те же call-сайты (0x81374, 0x8190c), что и call-граф Ghidra.

6. U-Boot

[факт] Из 108.86.0.118 блок bootloader снимается двойным cypher3: c3(c3(body)) → LOADER (MLO) + U-Boot.

Ключевые строки:

secure boot check success / secure boot check failed
yl_pubkey_verify_sigstr fail   yl_pubkey_create fail
ubifs crypto invalid magic=0x%8x   crypto is not a valid node
holtek e[set encrypt] / V[verify encrypt] / holtek enc=0x%08x
aes start / aes end
Hit any key to stop autoboot: %2d

[факт] Поиск адресов строк дал отрицательный результат (проверено несколько способов): - boot2.bin[0x3e3b0] = 0x4604B510 (Thumb push {r4,lr}; mov r4,r0), а не 0x000480C8; - ни одного 4-байтного слова, равного 0x000480C8 (ubifs crypto invalid magic) или 0x000547EC (secure boot check failed); - формула VA = base + (off − C) не дала совпадений ни для C ∈ {0, 0x10000, 0x20000, 0x30000, 0x40000}, ни для base ∈ {0, 0x60000000, 0x61000000, 0x61C00000, 0x08000000, 0x20000000}; - Thumb ADR (0xA0xx) к этим строкам не ведёт.

Вывод: ссылки на строки не являются простыми абсолютными литералами в этом файле. Для разбора нужен нормальный загрузчик в Ghidra (raw-import с выбором базы и режима по функциям) либо дамп/консоль устройства. Скан «base + stroff» по всему файлу даёт ложный сигнал (много мелких чисел совпадает с началами строк).

mtdparts (rk_nand):

раздел offset size
ubl 0x00000000 0x100000
trust 0x00100000 0x080000
uboot 0x00180000 0x100000
env / userenv 0x00280000 / 0x00300000 0x080000
rfs 0x00380000 0x3780000
cfg 0x03B00000 0x0CC0000
rfs2 0x047C0000 0x3780000
klog 0x07F40000 0x0C0000

Загрузка: ubi.mtd=8 root=ubi0:rootfs ro rootfstype=ubifs ... ubi part rfs; ubifsmount rootfs; ubifsload ...; bootm. Есть ветки recovery: boottftp (tftp ... ${phonename}.bin; bootm), bootstorage (USB), bootram/smrfs.

[факт] ubl и trust в пакет не входят — пакет содержит только version, rfs, bootloader; bootloader пишется в uboot (+копия).

7. Rootfs

  • [факт] rfs (86.0.118) = cypher3 → LZMA → 43 655 168 Б → UBI#, min_io 2048, LEB 0x1F000, PEB 0x20000, 331 блок, том rootfs.
  • [факт] UBI-заголовки big-endian; отображение PEB→lnum линейное (PEB2→lnum0 …), т.е. перестановки нет.
  • [факт] В томе нет UBIFS-суперблока: LEB0 = 4096 Б блоба + 0xFF до конца. Мастер-узлы UBIFS целы в LEB1 и LEB2 (sqnum 35003/35004).
  • [факт] Крипто-формат покрывает почти весь том: 315 из 331 LEB начинаются с magic 38 26 90 05 (0x05902638) — это vendor-узел ubifs crypto, а не UBIFS. Плаинтекстовых UBIFS-LEB всего 9 (типы: 7 master ×2, 10 commit-start ×1, 9 index ×6) + 6 стёртых.
  • [факт] Типовой заголовок crypto-узла (пример LEB10): 38 26 90 05 | d4 6a 0b 27 | 04 00 00 00 | ... — magic, 4 изменяющихся байта, далее счётчики/поля, затем зашифрованное тело.
  • [факт] Литерала 0x05902638 в U-Boot нет — константа собирается инструкциями (Thumb-2 movw/movt) либо проверяется после расшифровки; статический поиск по байтам не сработал.
  • [факт] SoC: Rockchip RK3308 (строки rk3308_nfc, rk3308_spi_nand_read_page_hwecc).
  • [факт] Блоб LEB0 на 96% периодичен с шагом 16 Б — сигнатура блочного шифра (AES-ECB по константному plaintext); простой XOR с периодом 16 не подходит (конфликты ключа).
  • [факт] ubireader_extract_files без суперблока не разбирает (0 файлов).

Следствие: ubifs crypto — не «защита суперблока», а слой над почти всей ФС. Оффлайн-сборка rootfs невозможна без схемы и ключа (Holtek) либо без собственного U-Boot/драйвера, который этот слой снимает.

9. Неизвестные

  2. Проверяет ли что-то содержимое пакета на V87 (в tool-блоке — нет; кандидаты: библиотеки rootfs, U-Boot).

10. Прошивка трубки 108.86.14.4 (2026-10-29)

[факт] Устройство: SIP-T43U, ПО 108.86.14.4, сборка 107.1.0.0.3.1.0, MAC 24:9A:D8:**:**:**, phone ID 2022********. Плата SIP-T43UMV17B (2021-11-12): RK3308H, DDR3, SPI NAND.

[факт] Пакет T46U(T43U,T46U,T41U,T48U,T42U)-108.86.14.4.rom (37 628 464 Б, sha256 c7c3f779c2b58c39ac3ed6c49763a55974f0034a8ce965ba660663e85b8efcb4) взят с atsvtule.ru; структура идентична 86.0.118:

ver 108.86.14.4  crypto 0x3  len 0x23E29B0  tail 0
  version     off 0x80      len 0x9CB50    cipher 0
  rfs         off 0x9CC50   len 0x22E5CDC  cipher 1
  bootloader  off 0x23829B0 len 0x60000    cipher 3

[факт] version.elf из 108.86.14.4 = 641 872 Б, sha256 0ccc8614fdf016e66cd82d1b6ed62e41bb0a8ad4eac07bd44dd0de9343d6f20a — байт в байт совпадает с version.elf из 108.86.0.118. Отличий нет: статическая сборка, крипто-импортов нет, проверки — magic / CRC заголовка и блоков / размер распаковки.

[факт] Пересборка identity: rombuild.py → True, sha256 совпал. Пакет-проба с версией выше: old/test_108.86.14.99.rom, sha256 0d9f221af1824b876102fc1812e6c36b51f6fbbe6b779567391f37e9107ba499.

[следствие] На этой трубке RSA/AES-проверки пакета нет — маршрут без ключей (V86) к ней применим. Ограничения: версия в пакете должна быть выше текущей (дилер пишет, что возврат к v85 невозможен), а содержимое rfs по-прежнему упирается в слой ubifs crypto для правок ФС.

[факт] rfs этой прошивки распакован (cipher 1 → LZMA → 44 834 816 Б, начинается с UBI#). UBI: PEB 0x20000, vid_hdr_offset 0x800, data_offset 0x1000, LEB 0x1F000, 342 PEB. Классификация LEB: 324 crypto (38 26 90 05), 9 обычных UBIFS-узлов (типы 7×2, 10×1, 9×6), 6 стёртых, 3 прочих. То есть слой ubifs crypto в 86.14.4 тот же, что в 86.0.118.

[факт] В version.elf нет строк вида «older/downgrade/newer» — проверка версии, если есть, живёт в прикладном ПО rootfs (version, blk version — это про CLI-опции самого апдейтера).

11. Эмулятор апдейтера: откуда берётся публичный ключ (2026-10-29)

Работа велась на version.elf 108.87.0.20 (sha256 2747b898…) в Unicorn. Инструменты: tools/emu.py (загрузка PIE, резолв импортов через .rel.plt → sentinel-GOT, хуки libc/OpenSSL), tools/disasm.py, tools/funcs.py, tools/probe_*.py.

Адреса. [факт] Адреса Ghidra = файловые + 0x10000. Проверено по телу: Ghidra FUN_00082170 = файл 0x72170, длина 2404 Б, конец 0x72ad4 — совпало с базой функций Ghidra.

Алгоритм FUN_00082170(blob, 0x200, type). [факт] Возвращает 550-байтный DER SubjectPublicKeyInfo (30 82 02 22); сборка:

  1. memset(buf1, 0, 0x400), memset(buf2, 0, 0x400), memcpy(table, 0x76e98, 0x806).
  2. 32 × SHA1(blob[16i : 16i+16]) → первые 16 Б каждого дайджеста в buf1[16i].
  3. Далее цепочка по 64 слотам buf1: 3168 вызовов SHA1 по 16 Б, затем 1584 × SHA256 (по 32 Б на месте) и 792 × SHA512 (по 64 Б на месте).
  4. buf2[i] = buf1[table16[3+i]] для i < table16[2]; длина 0x226 = 550.
  5. BIO_new_mem_buf(buf2, 550) → d2i_RSA_PUBKEY_bio.

[факт] Параметр type на результат не влияет (проверено 0, 1, 2 — выход побайтово тот же).

Кто вызывает. [факт] Ровно два места: FUN_0007f778 (файл 0x6f778, вызов 0x711a8) и FUN_00083d04 (файл 0x73d04, вызов 0x73d5c).

Источник блоба. [факт] Эмуляция FUN_0007f778 с хуками open/readlink/lseek/mmap:

readlink("/proc/self/exe")            → сам апдейтер
open(<апдейтер>, O_RDONLY); lseek(fd, 0x10000)
open("/tmp/kdgw123", O_WRONLY|O_CREAT|O_TRUNC)
open("/dev/keypad0", O_RDWR)          → ioctl 0x80205810 / 0x40045812 / 0x80045813 (MCU)
open("/dev/mem", O_RDWR|O_SYNC)       → mmap(0, 0x200000, RW, SHARED, fd, 0)
FUN_00082170(mmap + 0x100, 0x200, mmap[0x808])

[факт] То есть 512-байтный блоб берётся из /dev/mem по смещению 0x100, байт типа — по 0x808. Пути /dev/mem и /dev/keypad0 в бинаре зашифрованы: в strings их нет, собираются в рантайме.

Проверки кандидатов. [факт] DER не получился ни для: version.elf+0xf10 (энтропия 7.60, 220 разных байт), version.elf+0x59460, шапки ROM, хвоста ROM, заголовка вложенного ROM, тела version-блока; скан boot2.bin и version.elf шагом 0x1000 — 0 совпадений.

Вывод. [факт] В 87.x публичный ключ выводится из содержимого памяти устройства, а не из пакета. [гипотеза] Это ключевой блок, который загрузчик кладёт в начало DRAM при старте; он одинаков на всех аппаратах (иначе один пакет не подходил бы всем).

Следствие. Оффлайн-путь упирается в 512 Б + 1 байт с устройства — на порядок дешевле полного дампа флеша: при наличии root достаточно dd if=/dev/mem bs=1 skip=256 count=512 и чтения байта 0x808.

Открытый вопрос. [гипотеза] Возможное расхождение эмуляции: не выполняются конструкторы (.init_array), не проверены значения DAT_00099074 / DAT_000990a0 / DAT_00099220 из .data, на которых стоят opaque-предикаты OLLVM.
