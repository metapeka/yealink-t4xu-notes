    Ветка D — подмена содержимого rfs без вендорского формата

    Черновик проекта. Статус: [гипотеза], проверяется только на доноре.

    Важно. Это не дешёвая альтернатива ветке B. Ядро /uImage лежит в том же томе rootfs (ubifsload 0x00C00800 /uImage), а том на 324 из 342 LEB зашифрован (38 26 90 05). Значит собрать загружаемый образ «с нуля» нельзя: нет ни содержимого ФС, ни ядра. Ветка D зависит от того же, что и ветка B — ключа Holtek или дампа флеша. Механику записи она упрощает (не нужен свой апдейтер), но не снимает зависимость.

    Идея

    Апдейтер пишет блоки в /dev/mtdN «как есть»: у него есть типы none|bin|tool|file|nand-raw|nand-oob|nor (строка справки в version.elf). В пакете 108.86.14.4 блоки размечены так:

    блок type cipher что лежит внутри
    version 2 0 ELF-программа (сам апдейтер)
    rfs 4 1 LZMA → UBI, LEB в обёртке 38 26 90 05
    bootloader 4 3 cypher3 → LOADER + U-Boot

    [гипотеза] type 2 = tool (исполняемый образ), type 4 = nand-raw (сырые страницы во флеш). Значит полезная нагрузка rfs пишется в раздел дословно, без переупаковки в UBIFS: апдейтер не знает про UBIFS и crypto, он просто копирует байты.

    Отсюда: если собрать пакет с rfs, внутри которого лежит обычный UBI/UBIFS (без обёртки 38 26 90 05), апдейтер запишет его так же дословно.

    Что остаётся непроверенным

    U-Boot в строке ubifs crypto invalid magic=0x%8x явно проверяет magic. Два исхода:

    1. Magic отсутствует → LEB считается обычным, монтируется штатным ubifs — [гипотеза A], тогда всё работает без патча загрузчика и без ключа.
    2. Magic обязателен → отказ монтирования, аппарат не грузится — [гипотеза B].

    Различить можно только на доноре (или по живому логу UART).

    Порядок проверки на доноре

    1. Контроль. Официальный 108.86.14.4 — убедиться, что пакет ставится и аппарат грузится (базовая линия).
    2. Проба версии. old/test_108.86.14.99.rom — доказать, что пересобранный пакет принимается (меняется только строка версии).
    3. Проба формата. Пакет, где rfs — заведомо валидный обычный UBIFS с тем же ядром/init (минимальное изменение: добавить один файл). Смотреть, дойдёт ли до монтирования.
    4. Откат. Держать под рукой официальный пакет; UART-лог обязателен.

    Что нужно, чтобы собрать пакет шага 3

    • mkfs.ubifs с параметрами: -m 2048 -e 126976 -c 2047 (LEB 0x1F000 = 126 976) и ubinize с -p 0x20000 -m 2048.
    • Содержимое: распакованный текущий rootfs. Проблема: содержимое ФС мы не видим — 324 из 342 LEB зашифрованы. То есть свой UBIFS «с нуля» придётся собирать из нуля (busybox + init), а не из текущего образа.
    • Проверка размера: payload LZMA(cipher 1) не должен превысить 0x22E5CDC; rebuild.py пересчитает length, block_total и header_crc.

    Ограничения

    • Шаг 3 выполним только после расшифровки ФС (ключ Holtek) или дампа флеша — до этого содержимого и ядра для нового тома нет.
    • Без донора шаги 2–3 не выполнить.
    • Если гипотеза B верна — остаётся только ветка B (дамп + патч U-Boot).
    • Ядро и /uImage живут в том же томе rootfs (ubifsload /uImage), значит свой образ должен содержать и ядро, и ФС.

    Про kenv — не тупик, но и не переключатель

    В U-Boot есть строки UB-N:kenv(%d,0x%llx) check read crypto=0/1 и kenv(%d) master->backup / crypt=%d. Судя по соседним сообщениям (save master/backup, check failed to crc), crypt=%d — это шифрование самого блока env и его копий, а не флаг слоя ubifs crypto. Как способ отключить слой не рассматривать.
